## Why now

`docs/ROADMAP.md` states every **technical** gate for 1.0 was shipped in v0.31.0 (public-API baseline,
semver policy, consolidation reviews, hosted repo + release CI, SourceLink, final API sign-off — all ✅).
The one stated remaining gate is **adoption**: *"1.0 tags only after more applications adopt Lyntai in
anger and the surface survives that contact (the sibling apps + at least the agent-manager desktop
integration running on it)."*

That gate is now essentially met. Three real consumers in the sibling workspace reference Lyntai and
all pin the latest **0.31.1**:

| Consumer | Lyntai packages | Version |
|---|---|---|
| Sibling server A | Core, Storage.Sqlite, Providers.ClaudeCli | 0.31.1 |
| Sibling server B | Core, Providers.ClaudeCli, Storage.Sqlite | 0.31.1 |
| Agent-manager desktop app (manager + infrastructure) | Core, Storage.Sqlite, OpenAiCompatible, ClaudeCli, Tools.Mcp | 0.31.1 |

(The other sibling projects reference no Lyntai.)

The open backlog is down to **one conditional item** (JSON source-gen envelopes — only *"if
envelope-parsing bugs ever materialize"*, none have). So "complete everything towards 1.0" is **verify the
surface survived contact, land any final breaks before the permanent freeze, do the pre-1.0 migration
baseline reset, update docs, reach verified-green** — then tag 1.0.

## Decisions locked in brainstorming

- **Goal:** tag **1.0.0** now (adoption gate treated as met).
- **Migration squash:** Path A — **data-loss-OK reset** (consumers' Lyntai data is disposable dev data).
- **Final API review depth:** **thorough adversarial multi-agent pass** across all packable assemblies.
- **Consumer review:** **included** — read-only review of the 3 apps' Lyntai usage feeds the adversarial
  pass (no changes to those repos).
- **Release boundary:** work stops at **verified-green, ready to tag**; the human does the actual
  tag/`release.yml` (manual by D20) unless told otherwise.
- **Commits:** per logical unit, **never without explicit user approval** (repo rule, overrides the
  brainstorming skill's auto-commit).

## Sequencing (deliberate)

WS1 review → apply last breaks → WS2 squash (schema now final) → WS3 docs → WS4 version+baselines+verify.
Rationale: the squash bakes the schema into a baseline, so the schema must be final first; and API breaks
must land before the freeze (post-1.0 they gate a major bump).

  `Storage.InMemory`, `Storage.Postgres`, `Providers.ClaudeCli`, `Providers.ClaudeCli.Mcp`,

## WS2 — Migration baseline squash (per-domain, SQLite + Postgres)

### The constraint that decides the shape

**D15 selective migration is per-`StorageFeature` tag-driven** (`[Tags(nameof(StorageFeature.X),
StorageFeatures.AllTag)]`; a migration runs only when the runner's requested tags ⊆ the migration's tags).
A *single global* baseline could carry only one feature tag, so `UseSqliteStorage(path,
StorageFeature.Score)` would over- or under-create tables. **Therefore the squash keeps one baseline PER
domain**, not one file. (Single-file baseline rejected — it breaks a shipped feature.)

### Target: 9 domain baselines per backend

Each domain collapses to ONE migration that folds its ALTERs into its `CREATE`, keeps its
`[Tags(nameof(StorageFeature.X), StorageFeatures.AllTag)]`, and is renumbered under one fresh monotonic
date (e.g. `202608010001`..`202608010009`), never reusing an old number.

**SQLite — 16 files → 9 baselines:**

| Domain (StorageFeature) | Folds these current migrations | Notes |
|---|---|---|
| KeyValue | 170001 | — |
| Conversation | 170002 | — |
| Memory | 170003 + 170007 (Ttl) + 220002 (LastAccessed) | FTS5 trigram + 3 triggers + backfill; `CAST` on any real cols |
| Score | 170004 | `CAST(x AS REAL)` on score/double cols |
| Trace | 170005 + 170008 (TraceId) | — |
| PromptVersion | 170006 | — |
| Jobs | 180001 (priority already folded pre-release) | — |
| Governance | 180002 (response cache / usage / vector) | — |
| CuratedMemory | 180003 + 220001 (TaskScope) + 270001 (Title) + 270002 (Search) + 270003 (Metadata) | FTS5 search table + relational metadata index |

**Postgres — 14 files → 9 baselines:** same domain split. Postgres already lacks separate `170007`/`170008`
(folded pre-release), so Memory folds `170003 + 220002` and Trace is `170005`; CuratedMemory folds the same
four ALTERs. Preserve pg_trgm recall and the **lazy pgvector** schema (created on first use, not in a
migration — keep it out of the Governance baseline exactly as today).

### Reset semantics (Path A — data loss)

- Delete the old migration files. On upgrade, each consumer **drops its `lyntai_*` tables including
  `lyntai_version_info`** (or deletes the dev DB) so a fresh single-pass baseline applies cleanly. This is
  a **breaking** change, documented as a consumer migration note (WS3).

### Load-bearing safety check (the thing that makes this safe)

- **Schema-equivalence diff:** dump the fully-migrated schema (tables, indexes, triggers, FTS objects) from
  a **pre-change** build and a **post-change** build for BOTH backends and **diff — they must be
  identical.** A drift here is the primary risk; the diff is the gate.
- **Selective-migration tests:** a `StorageFeature` subset lands ONLY that domain's tables (D15 preserved).
- **FTS-recall tests:** Memory + CuratedMemory search still recall (incl. CJK substring) after the fold.
- **SQLite/Postgres parity** kept in lockstep (D12).
- Update the migration **count/version-list guards** (`MigrationRunnerTests`, `DeferredMigrationTests`).

**Exit criteria:** before/after schema diff empty on both backends; selective + FTS + parity tests green;
guards updated.

## Testing strategy

- **WS1:** TDD for fix-now changes; `ApiSurface` baselines updated deliberately per change.
- **WS2:** schema-equivalence diff (pre/post, both backends) · selective-migration tests · FTS recall ·
  SQLite/PG parity · migration-count guards.
- **WS4:** full `dev.mjs verify` gate (build + test + e2e + leak scan).

## Risks & mitigations

- **Schema drift in the squash** → the before/after schema diff is a hard gate.
- **Adversarial pass surfaces a break big enough to reconsider "tag now"** → surface it, decide explicitly
  (don't silently ship or silently drop).
- **3 apps need a coordinated DB reset** → documented migration note; applying it is on each app.
- **D15 selective migration regressions** → dedicated subset-migration tests in WS2.

## Out of scope

- Server/host/launcher/auto-update (permanent §9 exclusion).
- Cross-process global job-concurrency limits; streaming tool-calls; ClaudeCli/Local native tool-calling
  (roadmap deferrals, unchanged).
- Any change to the 3 consumer repos (WS1 consumer review is read-only).
